# Регрессионный UI-прогон «Копирки»

Самодостаточный дымовой прогон интерфейса в двух движках — headless Chrome
(`puppeteer-core`) и настоящий WKWebView (тот же движок, что у Tauri).
Дополняет `npm run smoke --workspace=server` (тот проверяет только HTTP API)
— здесь проверяется живой интерфейс: сетка, папки, поиск, диалоги, поповеры,
клавиатура. Задуман так, чтобы любой агент перед сборкой приложения одной
командой убедился, что правка ничего соседнего не сломала.

## Зачем два движка

Один и тот же баг — список папок в диалоге «Переместить в папку» открывался
в правом нижнем углу окна вместо места под полем (коммит 54c6287) — **не
ловится в headless Chrome**: причина в том, что Floating UI (библиотека
позиционирования Radix) сам компенсирует ошибку containing block у
`position: fixed` на Blink, но не на WebKit. Оба движка рисуют один и тот же
неверный DOM, но координаты на экране расходятся: Chrome «на глаз» рисует
всё верно, WebKit — нет. Настоящая «Копирка» — это Tauri, то есть WKWebView,
поэтому только WebKit-прогон (`webkit/run.mjs`) видит баг в чистом виде, по
геометрии. Chrome-прогон (`run.mjs`) ловит ту же причину структурной
проверкой `assertContainingBlockClean` (смотрит на само дерево DOM — есть ли
между поповером и `document.body` элемент, образующий containing block, —
а не на то, как Blink его отрисовал), не завися от того, докомпенсировал
её конкретный движок или нет. Оба прогона проверены в обе стороны на коммите
de63a43 (до фикса) и на HEAD. Чтобы повторить: `git show de63a43:web/src/components/ui/Modal.tsx > web/src/components/ui/Modal.tsx`
и то же для `Popover.tsx`, прогнать нужный `npm run test:ui[:webkit]`, затем
обязательно вернуть `git checkout -- web/src/components/ui/Modal.tsx web/src/components/ui/Popover.tsx`
и проверить `git status` по `web/` — пусто. Пока файлы подменены, других git-команд не выполнять.

## Запуск: Chrome (headless)

```bash
cd app
npm run test:ui
```

Поднимает временную песочницу (сервер + Vite + пустая библиотека во
временной папке), засевает её ~14 папками и 12 картинками через HTTP API,
прогоняет 13 сценариев в headless Chrome, гасит всё и удаляет песочницу. Код
выхода — `1`, если хоть один сценарий упал. Занимает ~15–25 секунд (бюджет —
1 минута).

Флаги: `--keep` (не гасить сервер/Vite и песочницу, вывести PID и путь),
`--out <dir>` (куда класть скриншоты, по умолчанию `tests/ui/.out/`),
`--server-port N` / `--web-port N` (по умолчанию **43121** и **5177**,
переопределяются и переменными `KOPIRKA_UI_TEST_SERVER_PORT` /
`KOPIRKA_UI_TEST_WEB_PORT`), `--sandbox-dir <dir>` (вместо `os.tmpdir()`).

### Требования к машине

- Node — использует `process.execPath` того интерпретатора, которым запущен
  сам `run.mjs` (никаких требований к PATH). Проверено на `$(which node)`
  (v22).
- Google Chrome — по умолчанию
  `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`, переопределяется
  переменной `CHROME_BIN`.
- Своя зависимость `puppeteer-core` — `npm install` внутри `tests/ui/` уже
  выполнен; `node_modules/` сюда не коммитится (правило корневого
  `.gitignore`, `node_modules/` без слеша в начале ловит и вложенные).

## Запуск: WebKit (WKWebView)

```bash
cd app
npm run test:ui:webkit
```

Та же песочница (сервер + Vite + библиотека, переиспользует `lib/processes.mjs`
и `lib/seed.mjs` из Chrome-прогона — отдельного стенда нет), но вместо
puppeteer — `webkit/wkprobe.swift`: маленькое родное окно WKWebView, которое
принимает JSON-сценарий шагов и отдаёт JSON с результатами. Safari через
`safaridriver` недоступен без ручного включения «Allow Remote Automation»
(настройка безопасности, включать самому нельзя), поэтому своё окно, а не
системный браузер. Занимает ~10–15 секунд (бюджет — 2 минуты), из которых
~4 секунды — старт и JIT-компиляция самого `swift`-скрипта.

**Важно:** у стенда нет настоящей мыши и клавиатуры — только
`WKWebView.evaluateJavaScript`. Клики и клавиши в `webkit/inject.mjs`
синтетические: `clickAt(x, y)` шлёт честную последовательность
pointer/mouse-событий в точку (это важно — часть обработчиков Radix и
`GridCard.tsx` реагируют на `pointerdown`, а не только на `click`), `key(k)`
— `keydown`/`keyup` на активном элементе. Реального колеса мыши в стенде
тоже нет: проверка «wheel не гасится» — синтетический `WheelEvent`, как и в
Chrome-прогоне, а не настоящая прокрутка (`page.mouse.wheel` есть только в
Chrome-версии сценария 5).

Флаги — те же, что у Chrome-прогона (`--keep`, `--out`, `--server-port`,
`--web-port`, `--sandbox-dir`), кроме `--sandbox-dir` по умолчанию свой
(`os.tmpdir()`, отдельная временная папка). Порты по умолчанию те же
43121/5177 — прогоны рассчитаны на последовательный запуск, не параллельный.

### Требования к машине (дополнительно к Chrome)

- `/usr/bin/swift` (Xcode Command Line Tools). Проверено на Swift 6.3.3.
- Никаких доп. npm-зависимостей — `webkit/run.mjs` использует только
  `node:child_process` (запустить `swift`) и переиспользует
  `../lib/processes.mjs`, `../lib/seed.mjs`, `../lib/helpers.mjs`.

## Изоляция

Порты песочницы (по умолчанию 43121/5177, общие для обоих прогонов) не
пересекаются с настоящим приложением Сергея (43117), чужим Vite (5173),
Storybook (6006) и песочницами других агентов (43118/5174, 43120/5176) —
список зашит в `run.mjs` и `webkit/run.mjs` (`FORBIDDEN_PORTS`), и прогон
откажется стартовать, если явно попросить один из этих портов. Библиотека,
конфиг и все файлы живут только во временной папке (`os.tmpdir()` по
умолчанию) и удаляются в конце.

Один нюанс адресов: Vite слушает `[::1]` (IPv6), а не `127.0.0.1`, если ему не
задать `server.host` явно (проверено `curl` и WKWebView ведёт себя так же) —
поэтому веб-адрес песочницы собран на `localhost`, а адрес сервера (он
слушает `127.0.0.1` явно, `server/src/index.ts`) — на `127.0.0.1`. Прокси
Vite (`web/vite.config.ts`) сам подставляет правильный `Origin` для
API-запросов из браузера, так что на работу это не влияет.

## Что покрыто (Chrome, `run.mjs`)

13 сценариев (`scenarios/01…13`), каждый — маленькая функция с ассертами по
геометрии/DOM, а не только «страница не упала»:

1. Сетка загрузилась — число карточек и число папок в сайдбаре.
2. Клик по папке фильтрует сетку; «Вся библиотека» возвращает всё.
3. Поиск по имени сужает сетку; очистка возвращает всё.
4. Поповер сортировки открывается точно под кнопкой (±2px) **и структурно**
   (`assertContainingBlockClean` — см. «Зачем два движка»), смена сортировки
   меняет порядок карточек (сверено с ответом API).
5. **Главный сценарий** — диалог «Переместить в папку»: список папок стоит
   точно под полем (±2px) и структурно чист (обёртка Radix Popper в
   `document.body`, без containing block на пути к ней), высота диалога не
   прыгает при открытии списка, колесо мыши реально скроллит список,
   синтетический `WheelEvent` из середины диапазона прокрутки (не с границы —
   см. «Грабли») не `defaultPrevented`, Esc закрывает сначала список, потом
   диалог.
6. Тот же диалог: выбор папки (клавиатура + клик) и сам перенос файла,
   подтверждённый через `GET /api/files/:id`.
7. «Добавить тег» из панели выделения — тег подтверждён через API.
8. Контекстное меню карточки открывается у курсора и структурно чисто; Esc
   закрывает.
9. Детальный просмотр (Enter на сфокусированной карточке) — список папок в
   панели деталей тоже проверен на позицию и структурно; Esc/Esc.
10. Настройки — панель на всё окно (не диалог), закрытие Esc и крестиком.
11. Корзина — удаление и восстановление файла.
12. FDB-10, «Горячие клавиши» в настройках: тогл прячет и возвращает
    поле-рекордер вместе с кнопкой сброса, клик по полю включает запись,
    ⌃ и ⌥ показываются живьём по мере нажатия, ⌃⌥K фиксируется, «Сохранить»
    доводит сочетание до конфига (сверено через `GET /api/settings`), кнопка
    сброса возвращает ⌥⌘C. Саму регистрацию хоткея прогон не проверяет —
    её делает оболочка Tauri, в браузере её нет (см. «Что не автоматизировано»).
13. За весь прогон в консоли браузера нет ошибок (`console.error`,
    `pageerror`) — единственное известное и отфильтрованное исключение:
    безобидный 404 фавиконки, которого нет в dev-сборке.

## Что покрыто (WebKit, `webkit/run.mjs`)

Один прогон WKWebView, 10 именованных проверок (не 12 — только позиционные/
структурные, ради которых стенд и существует; функциональность вроде поиска
или корзины уже покрыта Chrome-прогоном на том же React-коде):

1. User-Agent — sanity-проверка, что это правда WebKit, а не Chrome.
2–5. «Переместить в папку»: список под полем (±2px), containing block чист,
   высота диалога не прыгает, synthetic wheel не `defaultPrevented`, Esc
   закрывает список и затем диалог по отдельности.
6–7. Панель деталей: селект папки под полем (±2px) и containing block чист.
8–9. Поповер сортировки под кнопкой (±2px, `align="end"` — сверяются правые
   края, см. `assertUnderTrigger` в `webkit/run.mjs`) и containing block чист.

## Почему сценарий 5 (и его WebKit-аналог) — главные

Прямая проверка бага, из-за которого писался весь прогон (коммит 54c6287):
регрессия коммита cda3d4a портализовала поповер списка папок внутрь
`DialogContent` модалки, чтобы колесо мыши работало сквозь
`react-remove-scroll`. Но `motion` (пружина появления модалки) оставляет на
её теле `filter: blur(0px)` — а это тоже containing block для
`position: fixed`. Floating UI на WebKit не учитывает `filter` при расчёте
позиции (`isContainingBlock → !isWebKit()` в его исходниках), поэтому
смещение модалки складывалось со смещением списка дважды, и тот улетал в
угол окна; на Blink Floating UI это компенсировал, и баг был не виден. Фикс
вернул портал в `document.body` и решил прокрутку иначе: `onWheel` на самом
поповере гасит всплытие события до того, как оно дойдёт до `document`, где
`react-remove-scroll` мог бы его перехватить.

Отсюда две независимые проверки в обоих прогонах: геометрическая (ловит
регрессии позиционирования вообще, в любом из двух движков) и структурная
`assertContainingBlockClean` / `webkit/inject.mjs::measure` (ловит именно
эту причину — по дереву DOM, а не по итоговым координатам). На HEAD (после
54c6287) обе чисты в обоих движках. Откатите `Modal.tsx`/`Popover.tsx` к
`de63a43` — Chrome-прогон покраснеет на структурной проверке
(`«обёртка портализована в <div>, а не в document.body»`), а WebKit-прогон —
дополнительно на самой геометрии: список уезжает на **Δleft ≈ +421,
Δtop ≈ +257px** при окне 1280×760 (числа сняты живьём, см. «Доработка» в
корневом отчёте).

## Что не автоматизировано (проверять руками)

Всё из требуемого списка сценариев в итоге поддалось автоматизации. Из
смежного, что сознательно не стали покрывать:

- **Настоящее перетаскивание карточек** (drag&drop файла на папку сайдбара,
  `dnd.ts`) — в коде это ручной pointer-event протокол (HTML5 DnD в окне
  Tauri до страницы не доходит), а не нативный drag Chrome; воспроизвести его
  через `page.mouse.move` пошагово с моками `pointerId`/`setPointerCapture`
  чрезмерно хрупко для дымового прогона. Проверять руками: перетащить
  карточку на папку в сайдбаре, убедиться, что она подсвечивается лаймом и
  файл переезжает.
- **Импорт файлов через drag&drop из Finder / ⌘V из буфера** — оба идут через
  `DataTransfer`/`ClipboardEvent`, которые CDP не эмулирует так, чтобы нести
  настоящие бинарные файлы; сам HTTP-путь импорта (`POST /api/import`)
  подробно покрыт `server/src/smoke.ts`, а наш прогон засевает библиотеку тем
  же эндпоинтом.
- **Уведомления системы** (`KOPIRKA_QUIET`, десктопная обёртка Tauri) — вне
  веб-интерфейса, требуют собранного `.app`.
- **Настоящая регистрация глобального хоткея** (FDB-10) — её делает
  `desktop/src-tauri/src/shortcut.rs` через tauri-plugin-global-shortcut, и
  проверить её можно только в собранном приложении: нажать сочетание из другой
  программы и убедиться, что открылась рамка съёмки. Веб-часть (поле-рекордер,
  тогл, запись в конфиг) покрыта сценарием 12, серверная — дымовым прогоном.
- **Расширение Chrome** (FDB-03, подменю папок и блок «Сохранять в») — стенд
  поднимает только веб-интерфейс, расширение в него не загружается. Серверная
  половина (`folderId` в `/api/import/url` и `/api/import/capture`) проверена
  дымовым прогоном, целостность расширения — `extension/tools/verify.mjs`.
- **Реальное колесо мыши в WebKit-прогоне** — стенд синтетический (см.
  «Запуск: WebKit» выше); настоящую прокрутку колесом в WKWebView проверяет
  только Chrome-прогон (`page.mouse.wheel`) плюс ручная проверка в собранном
  приложении.

## Структура

```
tests/ui/
  run.mjs                 — Chrome: точка входа (песочница → сидирование → браузер → сценарии → отчёт)
  package.json             — своя зависимость puppeteer-core
  lib/
    helpers.mjs             — waitFor, rect/stableRect, containing-block, clickText/clickScope, api-клиент, ...
    processes.mjs           — spawn/остановка сервера и Vite, ожидание health (общий для Chrome и WebKit)
    seed.mjs                — генерация картинок (sharp) и наполнение библиотеки через API (общий)
  scenarios/
    01-grid-load.mjs … 13-console-errors.mjs
  webkit/
    run.mjs                 — WebKit: точка входа (та же песочница из ../lib/ → JSON-сценарий → swift → проверки → отчёт)
    wkprobe.swift            — драйвер WKWebView: JSON-шаги (goto/wait/waitFor/js/shot) → JSON-результат
    inject.mjs               — JS-хелперы, вставляемые в страницу (clickAt/key/measure — та же логика containing block)
    .out/                    — скриншоты последнего WebKit-прогона (в .gitignore)
  .out/                     — скриншоты последнего Chrome-прогона (в .gitignore)
```

## Как добавить сценарий

### Chrome

1. Новый файл `scenarios/NN-name.mjs` с `export default async function name(ctx) { ... }`.
   `ctx` даёт: `page` (puppeteer), `api` (HTTP-клиент к серверу песочницы),
   `seed` (`filesByName`/`folderIds`/счётчики из `lib/seed.mjs`), `shot(name)`
   (скриншот в `.out/`), `resetToLibraryRoot()` (вернуть сетку к «Вся
   библиотека», без поиска и выделения, дождавшись закрытия чужих диалогов).
2. Добавить импорт и строку в массив `SCENARIOS` в `run.mjs` — порядковый
   номер в имени файла и позиция в массиве должны совпадать.
3. Селекторы — по `role`/`aria-label`/тексту кнопки (см. `lib/helpers.mjs`:
   `findByText`, `findByAriaLabel`, `clickScope` для строк сайдбара — их
   текст в DOM склеен со счётчиком без пробела, отсюда отдельный помощник),
   не по Tailwind-классам: имена берите из `web/src/features/*` и
   `web/src/components/ui/*`, а не из макета — код первичен.
4. Для позиционных проверок используйте `stableRect`/`stableElementRect`, а
   не `rect` сразу после появления слоя: поповеры/модалки в редизайне
   анимируются пружиной (`motion-presets.ts`), и геометрия «прыгает» первые
   ~100–300мс. Для нового плавающего слоя на Radix Popper добавьте ещё
   `assertContainingBlockClean(page, selector, label)` — дёшево и ловит целый
   класс WebKit-специфичных багов, даже если геометрия в Chrome случайно сошлась.

### WebKit

Новый шаг — в `webkit/run.mjs::buildSpec`: добавить `js`/`waitFor`/`shot` в
общий список (один swift-процесс на весь прогон, отдельного окна на
сценарий не заводим — компиляция/старт стоит ~4с, дробить дорого) и функцию
проверки в `runChecks`, читающую нужный ключ из `results`. Для позиции
плавающего слоя — `window.__p.measure(triggerSel, layerSel)` из
`inject.mjs`, сравнивать через `assertUnderTrigger` (мерит `wrapper`, а не
`layer` — см. «Грабли»).

## Грабли, на которые уже наступили (чтобы не наступать снова)

- **`page.click(selector, {clickCount: 3})` для «выделить всё в поле» в
  headless Chrome ненадёжен** — синтетические mousedown/mouseup иногда не
  укладываются в окно, которое Chrome даёт тройному клику, и вырождаются в
  обычный клик. `Cmd+A` через `page.keyboard` тоже подводил. Рабочий способ —
  `setFieldValue` в `lib/helpers.mjs`: нативный сеттер `value` в обход
  React-обёртки + событие `input`.
- **Закрывающийся поповер ещё ~150–300мс кликабелен.** `glassLayerMotion` не
  ставит `pointer-events: none` на время exit-анимации — если под ним в этот
  момент окажется следующая цель клика (например, кнопка в подвале диалога
  под списком папок), клик поймает невидимый, но живой пункт списка, а не
  кнопку. После клика, закрывающего слой, дожидайтесь его реального исчезновения
  из DOM (`waitFor(... === 0)`), а не полагайтесь на факт клика.
- **Синтетический `WheelEvent` для проверки «не defaultPrevented» нечестен,
  если список уже докручен реальным колесом до границы** — `react-remove-scroll`
  легитимно гасит overscroll на границе (защита от утечки скролла наружу), и
  это не тот баг, который сценарий ловит. `dispatchWheelDefaultPrevented`
  принимает `scrollContainerSelector` и сам переставляет список в середину
  диапазона перед событием.
- **Диалог, оставшийся от упавшего сценария, может пережить `Esc`×2 дольше
  таймаута, а не просто медленно анимироваться** — на старом (сломанном) коде
  проверено: 12 секунд ожидания не помогли, диалог с мёртвым поповером внутри
  не закрывается вовсе. `resetToLibraryRoot` поэтому явно ждёт исчезновения
  `[role="dialog"]` из DOM после двух `Esc`, прежде чем кликать по сайдбару —
  иначе клик попадает в ещё живой скрим, а не в нужную строку.
- **Карточки нужно прокручивать в видимую область** перед кликом по «сырым»
  координатам (`page.mouse.click(x, y)`) — masonry-раскладка легко уводит
  карточку за нижний край окна. `page.click(selector)` и
  `ElementHandle.click()` это делают сами, `page.mouse.click(x, y)` — нет.
- **Двойной клик puppeteer по карточке сетки её не открывает** — в
  `GridCard.tsx` завязан pointer-down протокол переноса, который съедает
  быстрые повторные клики. Открывайте детальный просмотр как реальный
  пользователь с клавиатуры: клик (фокусирует и выделяет) → `Enter`. В
  WebKit-стенде, где нет настоящей мыши вовсе, проще: синтетический
  `dblclick` через `dispatchEvent` — он идёт в обход pointer-протокола
  напрямую в React-обработчик.
- **Vite слушает `[::1]`, не `127.0.0.1`**, если не задать `host` явно —
  адрес песочницы для веба собран на `localhost` (см. «Изоляция» выше).
- **Измеряйте `wrapper` (`[data-radix-popper-content-wrapper]`), а не первый
  найденный элемент внутри поповера, если это не сам контейнер.** Для
  поповера сортировки `layerSel` — это `[role="menuitemradio"]`, то есть
  ПУНКТ списка, а у пункта есть свой отступ от края контейнера (`p-1.5` слоя)
  — сравнение с триггером съезжало ровно на этот паддинг и путало его с
  настоящей регрессией позиционирования (поймано на первом прогоне
  WebKit-стенда: расхождение 7px там, где ожидалось ≤2px).
